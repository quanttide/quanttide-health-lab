# quanttide-health-lab

量潮健康管理实验室。

## fatigue-sources：从对话里找疲劳来自哪里

把「我最近很累」这种整体感觉，拆成能核对的几条来源：累是由哪一类事消耗出来的，
每一类给出原文里能对上的句子。

情感分析通常给一个分数（负面 62%），分数没法用——知道不开心，不知道为什么不开心。
这里换一个口径：**不说情绪是什么，说这股累从哪来，并且必须给原文作证。**

### 它产出什么

报告分两类信号出表，**不混**：

- **fatigue（真的累）**：说话人自己精力/心力被消耗——累、撑不住、提不起劲
- **friction（摩擦）**：事情反复、被替做决定、信息对不上、工具与协作不顺带来的烦躁与失控感

分开的原因：把「同一件事又说一遍还是没改」记成「累」，来源清单就会被摩擦占满，
真正的精力耗竭反而看不见。实测里两类数量差近十倍，合并报等于把结论写死。

形状是：

```
### 反复返工、说了又没改 —— 41 条（占摩擦命中 32%）
- 「刚才的 0.1.3 也不是我发的」        (2026-08-26 23:21，强度 2/5)

### 输出信息密度太大、看得吃力 —— 9 条
- 「我觉得当前的输出信息密度很大，负担很重」 (2026-10-21 16:43，强度 3/5)
```

每条来源带四样东西：命中条数、占该类命中的比例、原文证据句、时间。没有证据句的判定
一律不计命中——这条是硬口径，写在代码里（`llm.parse_items`），不靠叮嘱模型。

报告另有三节专讲可信度：责任归属（每条来源的消耗是谁造成的——助手没照做、助手输出太复杂、
用户自己、外部条件；不标主体，助手的不守约会被写成中性的「摩擦」，再变成用户该优化的东西）、
口径自检（规则词面信号与模型判定的一致率、未入选池的穿漏率）、
共现检验（有摩擦的日子疲劳命中率是否更高；差不到 1.5 倍就明说没有证据）、
自带偏差（语料只有与 AI 的对话、单模型单次判定、来源是假设不是因果）。

### 流水线

```
extract  → 会话库抽用户消息      data/messages.jsonl
screen   → 宽筛候选 + 留未入选池  data/candidates.jsonl / data/rest_pool.jsonl
annotate → 逐条判定（断点续跑）   data/annotations.jsonl
probe    → 未入选池抽样反查       data/probe.jsonl
report   → 汇总成报告             reports/<name>.md
```

每步一条命令、一份产物，互不覆盖，重跑安全。`annotate` 已标的跳过，只补缺。

```bash
python -m fatigue_sources extract
python -m fatigue_sources screen

# 先小样本试口径，够了再全量
python -m fatigue_sources annotate --limit 40 --batch 20 --workers 4
python -m fatigue_sources annotate --batch 20 --workers 4

python -m fatigue_sources probe --n 60
python -m fatigue_sources report --name 2026-10-fatigue
```

一次跑完：`python -m fatigue_sources run --probe`。

结论不由脚本写：把结论写进一个 md，`report --conclusion 结论.md` 会拼到报告末尾。
脚本永远只出数字，判断留给人。

### 判定口径

写在 `fatigue_sources/annotate.py` 的 `SYSTEM` 里，改口径只改 prompt，不事后改数据。

- 只判说话人自己的状态：技术提问、下命令、纠错都不算
- 有疲劳词不等于在说自己累（「这个报错让人很烦」是对工具的抱怨）
- 允许隐式疲劳：靠语气（回避、推迟、自嘲、放弃）看出的负荷，标 `implicit`
- 来源必须是口语短语、6–16 字、能对上原句；「工作压力」这种空泛词判不合格
- 证据句必须原样截取原文连续片段，不得改写、拼接

### 隐私边界

- 代码可公开（Apache-2.0），语料不出本机：`data/`、`reports/` 全部在 `.gitignore` 里
- 语料只取 Hermes 会话库（`~/.hermes/state.db`）里 `role='user'` 的消息，只读打开
- 判定需要调用模型，因此消息正文会发到模型服务商（默认 DeepSeek）：要纯本机就把
  `FATIGUE_API_BASE` 指向本地 OpenAI 兼容端点
- 报告里的证据句过一遍脱敏（密钥、邮箱、长串），证据仍可与原文核对

### 凭据

`llm.resolve_key()` 先读环境变量 `DEEPSEEK_API_KEY`，读不到再从 `~/.bashrc` 的 export 行
解析——Hermes 的凭据池记的是 `env:DEEPSEEK_API_KEY`，非交互进程拿不到，所以自己解析一次。

环境变量：`FATIGUE_MODEL`（默认 `deepseek-chat`）、`FATIGUE_API_BASE`。

### 已知限制

- 只覆盖与 AI 的对话；与人当面聊的话、会议录音都不在语料里（要接就换 extract 那一层）
- 单模型单次判定，没有第二人复核；来源短语是概括，不是因果推断
- 命中要求来源与证据句成对出现，语气很轻的累会被漏掉；穿漏率由 `probe` 量出来，报告里报
- 会话里 AI 的提问方式会塑造他的说法，标注无法把这一层剥掉
- 有一类边界判不准：分析「读者会怎么累」时主语是读者，但里面混着他自己的负担感

### 跑过一遍的结果（2026-10）

语料 2257 条用户消息（去重后；Hermes 的消息表会留下被吸收的副本，同会话同内容只算一条），
判定 1582 条，未判定池 120 条抽样反查穿漏 2 条。结果是两类信号数量差三倍以上，而且来源完全不同：
疲劳指向理解成本，摩擦指向信息传递走样。结论写在本地 `reports/` 里，不入仓（含原文）。

去重这一步不能省：不去重时同一个「累」会被算两三次，命中数虚高三分之一。
